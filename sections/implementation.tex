\chapter{Implementation} \label{cha: implementation}
This Chapter presents the implementation of  \acs{ReID} module, \acs{SR} module and how they are combined. The description include details on dataloader, training hyperparameters, validation strategy and training duration. To evaluate the hypotheses outlined in Section \ref{sec:hypotheses}, four model configurations have been implemented, and will be compared against each other.

\section{ReID Module}
This section presents the implementation details, when it comes to the \acs{ReID} module, including the dataloader, training hyperparameters and training setup. 

\subsection{Dataloader}
The data loaders used for person \acs{ReID} training, validation, and testing are implemented using the \texttt{DataLoader} class from \texttt{torch.utils.data}. For training, the data loader operates on the combined dataset described in Section~\ref{combineddataset}, using a batch size of 64 with data shuffling enabled. This configuration ensures hat each batch has images from different datasets.

For validation and testing, the data loaders use a batch size of 1 and disable shuffling. This setup follows standard person \acs{ReID} practice, as each image is evaluated independently to enable precise query–gallery matching and reproducible performance measurement.

\subsection{Re-Implementation of OSNet}\label{sec:implementationosnet}
The architecture of the implemented person \acs{ReID} model is identical to what described in Section \ref{sec:methodreid}. The implementation of the \acf{OSNet} architecture is taken from the \texttt{Torchreid} repository, which also comes with a pretrained \acs{OSNet} model \cite{TorchReIDM1501}. However, to ensure full control over the training process and to train from scratch, a custom training script was made.

The training hyperparameters is mostly based on the ones applied in the original OSNet paper \cite{OSNet}, but some changes have been made to optimize training. \noindent Both the baseline and the augmented version are trained using \acf{SGD} optimizer with a momentum set at 0.9 and a weight decay of \(5e-4\), as this optimization were used in the original implementation and training of OSNet \cite{OSNet}. Although other setups were tried, see Appendix \ref{alternative training setups}, when it comes to learning rate and milestones for the \texttt{MultiStepLR}, it was found, that the hyperparameters used in the paper, resulted in the best validation results. For this reason is the learning rate \(65e-3\), milestone 150, 225, 300 and gamma factor 0.1.
\\\\
The number of epoch are kept the same as well, expecting a convergence before reaching 350 epochs. Keeping a large number of epoch ensure that convergence can be reached within one training, while still keeping the flexibility of early stopping.
\\\\
As introduced in Section \ref{sec:reidloss}, the loss function used for training is the multiclass cross-entropy loss. In practice, this is implemented using the \texttt{CrossEntropyLoss} module from the \texttt{torch.nn} library, which provide built-in label smoothing via input parameter. Label smoothing is applied with a factor of 0.1, limiting the confidence of the predicted class probabilities and thereby reducing overfitting to training identities. This regularization is particularly beneficial for the open-set learning setting of person \acs{ReID}, as it encourages the model to learn more robust and transferable feature embeddings, as discussed in Section~\ref{sec:reidloss}, as described in Section \ref{sec:reidloss}.

\subsection{Validation strategy}
During training the learning of the models are monitored using the validation set introduced in \ref{trainingstragegyreid}. As the augmented version is trained using augmentations, the same augmentations are used on validation set. This strategy selection of the model with best performance on the augmentations. The performance are measured using the metrics: Rank1, Rank5, Rank10, Rank20 and \acs{mAP} from Section \ref{reidmethodevalmetric}.
\\\\
The model's performance was monitored through periodic validation:
\begin{itemize}
    \item For epochs 1 - 200: validation is performed every 10 epoch
    \item For epochs 201 - 350: validation frequency increases to every 5 epoch
\end{itemize}

\noindent This adaptive validation strategy allows for more frequent monitoring as learning rate drops, and the training approaches convergence. Training ran for a total of 350 epochs without early stopping, though checkpoints were saved every validation. From these saved checkpoints is the final model selected based on the best \acs{mAP} score.

\section{SR Module}
This section describes how the \acs{SR} module, using the previously described \acs{EDSR} architecture, was configured and trained for this project.

\subsection{Dataloader}
The dataloader for the \acs{SR} module loads paired \acs{LR} and \acs{HR} images from the \acs{DIV2K} \cite{Agustsson2017NTIRE} and \acs{RELLISUR} \cite{aakerberg2021rellisur} datasets. The two datasets were kept separate during training to accommodate their different degradation characteristics, as described in Section \ref{SRtrainingdata}.

\subsection{Re-implementation of EDSR} \label{sec:implementationedsr}
The implemented version of the \acs{EDSR} architecture was taken from the source code from the original paper for \acs{EDSR} \cite{lim2017edsr}. One modification was made: image normalization is performed in the dataloader instead of inside the network. This simplifies integration with the \acs{ReID} module, as both modules can use the same preprocessing.
\\\\
All images are normalized to the range $[-1, 1]$ by subtracting 0.5 and dividing by 0.5 for each color channel. This normalization is applied to both \acs{LR} and \acs{HR} images, ensuring that the model learns to produce outputs in the same range as the target images. The training script is implemented from scratch to ensure full control over the training process.

\noindent The training follows the two-stage strategy outlined in Section \ref{SRtrainingdata}: Stage 1 trains from scratch on \acs{RELLISUR}, while Stage 2 finetunes the best checkpoint from Stage 1 on \acs{DIV2K}. Both stages use the Adam optimizer with momentum parameters $\beta_1 = 0.9$ and $\beta_2 = 0.999$, as this is the standard optimizer configuration used in the original \acs{EDSR} implementation \cite{lim2017edsr}. A batch size of 16 is used for both stages.
\\\\
For Stage 1, a learning rate of \(1 \times 10^{-4}\) is applied to enable rapid learning from random initialization. The model is trained for 200 epochs. For Stage 2, the learning rate is reduced to \(5 \times 10^{-5}\) to preserve the learned representations while allowing gradual adaptation to the new dataset. This reduction is critical for finetuning, as it prevents forgetting of the pretrained features. The model is trained for 100 epochs during finetuning.
\\\\
The loss function used for training is the L1 loss, as described in Section \ref{sec:srloss}. This is implemented using the \texttt{L1Loss} module from the \texttt{torch.nn} library.

\subsubsection{Validation Strategy}
Validation was performed at the end of each epoch using the \acs{RELLISUR} validation split for both training stages. The validation pipeline computed both validation loss (L1) and validation \ac{PSNR} to monitor training progress. Model checkpoints were saved every 10 epochs, and the best model based on validation \ac{PSNR} was saved separately for final evaluation. Using the same validation set for both stages ensures consistent evaluation and allows monitoring whether the model retains its ability to handle realistic degradations after finetuning on synthetic data.

\subsubsection{Training from Scratch on \acs{RELLISUR}}
Stage 1 employed the patch-based training strategy described in Section \ref{SRtrainingdata}, where aligned \acs{LR} and \acs{HR} patches of size \textit{64×128} and \textit{128×256} pixels respectively were randomly cropped from \acs{RELLISUR} image pairs during each training iteration. \subsubsection{Data Augmentation}
The data augmentation strategy outlined in Section \ref{SRtrainingdata} was applied during both training stages. Horizontal flip and brightness change were applied with synchronized random states between \acs{LR} and \acs{HR} images to maintain correspondence, which is required for supervised super-resolution training. Gaussian noise (mean: 0.0, std: 0.1) and Gaussian blur (kernel size: 7, sigma: [0.1, 2.0]) were applied only to the \acs{LR} images to simulate realistic acquisition artifacts commonly found in surveillance imagery, while keeping the \acs{HR} targets clean. \noindent This model used \acs{EDSR} and \hyperlink{model:baseline}{Baseline model}, with pretrained weights from the best performing epoch from their respective training runs. No further training or finetuning was performed, and the model served no purpose beyond evaluating \hyperlink{hypothesis:1}{\textit{Hypothesis 2}} in Chapter \ref{cha: experiments and results}. 
\\\\
To fully asses the impact of implementing a \ac{SR} system with \acs{ReID}, a script was created to evaluate a sequential combination of the two models, where the data is first passed through the trained \acs{SR} model, whose output is then fed into the trained \acs{ReID} model. The efficiency of this setup is expressed with error metrics \acs{mAP} and Rank-1, and can then be compared with other evaluation instances, such as the same \acs{ReID} model without the \acs{SR} module. 
\\\\
This sequential evaluation script is used to test the \acs{ReID} model on its own and together with the \acs{SR} module. The models are already trained and are not updated in this step, as the script only runs inference to evaluate performance.

The dataloader discussed in \ref{imp_dataloading} was also used in conjunction with this script, but mostly with a distinct emphasis on the evaluation part, such as query and gallery for the relevant \acs{ReID} datasets.

\section{Implementation of End-to-end ReID and SR}
Since the \acs{SR} module was trained to clean and upscale on diverse images, it is not specialized for the domain of person \acs{ReID}. By combining the two modules end-to-end, the \acs{ReID} loss can flow back into the \acs{SR} module, ideally forcing it to learn specific cleaning or sharpening operations that improve the final \acs{ReID} task, while the \acs{ReID} can simultaneously learn to extract features from a \acs{SR} input. This effect can be seen in Figure XXX (sammenligningsbilleder, måske i resultater eller her?). 
\\\\
This model used the setup and pretrained modules as the \hyperlink{model:sequential}{Sequential model}, with the difference being that training was resumed. The training itself was done under the same configuration/method/settings/hjælp as the standalone \acs{OSNet} models described in Section \ref{sec:implementationosnet}. The only notable changes were in the number of total epochs, the chosen milestones for the learning rate scheduler, and the chosen learning rates for each module. One further addition is the option of freezing an individual module, this was however only utilized for the \acs{ReID} module. The training hyperparameters can be seen in Table \ref{tab:endtoendtrainingparameters}.

\noindent The model was trained using the strong augmentation pipeline, seen earlier in Table \ref{tab:three_subtables}, for the purpose of retaining the \acs{EDSR} model's robustness to poor image conditions. In order to still give \acs{EDSR} the chance to adapt to low resolution person images, the \acs{ReID} module was frozen for the first 20 epochs. In practice, freezing the module meant setting \texttt{module.eval()} and \texttt{require\_grad = False} for each its parameters. This action was then reversed during training by setting \texttt{module.train()} and \texttt{require\_grad = True}. The choice of freezing the \acs{ReID} module was made for the purpose of letting the \acs{SR} module adapt to the new domain and loss metric.
\\\\
The learning rate is flipped. 
\\\\
\noindent To benefit from the end to end integration of the two models, training was continued with pretrained weights from baseline \acs{OSNet} and \acs{EDSR}. \acs{OSNet} weights were frozen for the first 20 epochs, such that \acs{EDSR} could adapt to the new data being \ac{LR} images of people, instead of the more diverse nature of \acs{DIV2K} and \acs{RELLISUR}. While only a classification loss back-propagated, it should still help specialize the model for the task, as can be seen in Section XXX. The learning rate for \acs{EDSR} was chosen at \texttt{65e-4}, due to it being a middle point between the training and finetuning learning rate used during the standalone training. The learning rate for \acs{OSNet} was set to \texttt{1e-4}, such that it would drop to \texttt{1e-5} after the the first milestone, which coincides with \acs{OSNet} being unfrozen. This was chosen as the model had already learned the task of \acs{ReID}, and in this end-to-end training should focus on learning to extract features from \acs{SR} images. A second milestone was set at epoch 60 for final finetuning with the lowest learning rate. Training concluded at epoch 100, at which point the model had learned enough for a fair comparison with the other models, even if more performance could have been squeezed out.

\section{Deployment}
\label{deployment}
As the \acs{ReID} system was made with the intention to be utilized in a real-world setting, a script was created that allows it to be deployed on a third-party system with API functionality, as to facilitate its use by other external systems and users if needed.
\\\\
To ensure a more streamlined implementation of the system in future uses, the deployment was made with a Docker containerization setup. This ensures that relevant libraries, dependencies, and any other version-specific parameters needed to run the script, are present and being used. Furthermore, a requirements text file with used libraries and corresponding versions has also been included to allow reproducibility of the container or another virtual environment if needed.
\\\\
The deployment script utilizes the \texttt{FastAPI} library as its core framework for web related communication. This is specifically chosen because of its ease of use, yet powerful foundation, and tools. As deployment was not the primary focus point of this project, only a simple \texttt{GET} and \texttt{POST} request method were integrated in the script, which runs through hard-coded image directories located in the server. with little to no front end in mind. If implementation on a real system was the end-goal of this project, more work should be done to achieve an acceptable industry standard.
\\\\
The backend pipeline of the deployment script works by first processing the gallery and query image(s) from a \texttt{.JPG} filetype to a \texttt{base64} encoding and a tensor. The tensor contains the image with preprocessing applied, such as normalization and image resizing, which is done to align with the \acs{ReID} models architecture for optimal compatibility. Alternatively, the \texttt{base64} encryption is a copy of the non preprocessed image that is used to make file handling between the client and server more efficient. Subsequently, the tensors for query and gallery are computed by the \acs{ReID} model, which returns the best matches back to the client. A simple HTML setup has been created to integrate some visualization for the front end by displaying the returned matches with a ranking order and the original query image for comparison as seen in Figure \ref{fig:deployment_example}.
