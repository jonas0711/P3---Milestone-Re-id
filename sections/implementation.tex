\chapter{Implementation} \label{cha: implementation}
This Chapter presents the implementation of the dataloaders, the chosen \acs{SR} and \acs{ReID} architecture, training scripts, and the combination of the models. To evaluate the hypotheses outlined in Section \ref{sec:hypotheses}, three model configurations have been implemented, and will be compared against a baseline model. 

\section{ReID Module}
This section presents the implementation details, when it comes to the \acs{ReID} module, including the dataloader, model configuration and training setup. 

\subsection{Dataloader}
The dataloader for the training on \acs{ReID} were built using the \texttt{DataLoader} class from \texttt{torch.utils.data}, designed to generate batches of data samples for training, validation and test.
The dataloader combines the three datasets presented in Section \ref{sec:trainingstragegyreid}, using the \texttt{Dataset} and \texttt{DataLoader} classes from \texttt{torch.utils.data}, enabling joint training across all of them. 

\subsection{Re-Implementation of OSNet}\label{sec:implementationosnet}

\noindent Both the baseline and the augmented version are trained using SGD optimizer with a momentum set at 0.9 and a weight decay of \(5e-4\), as this optimization were used in the original implementation and training of OSNet \cite{Zhou2019OmniScale}. A batch size is kept at 64, like in the paper, but the learning rate is changed from \(65e-3\) to \(1e-3\), because initial training showed XXXXXX. The number of epoch are kept the same as well, expecting a convergence before reaching 350 epochs. Keeping a large number of epoch ensure that convergence can be reached within one training, while still keeping the flexibility of early stopping.
\\\\
During training the learning rate is scheduled using a \texttt{MultiStepLR} with the milestones at 100, 175 and 250, where the learning rate is reduced with a factor of 10. This is as well different from the original training, because a plateau was hit early on in training of the two versions.
\\\\
As introduced in Section \ref{sec:reidloss}, the loss function used for training is the multiclass cross-entropy loss. In practice, this is implemented using the \texttt{CrossEntropyLoss} module from the \texttt{torch.nn} library, which provide built-in label smoothing via input parameter. Label smoothing is applied with a factor of 0.1, limiting the confidence of the predicted class probabilities and thereby reducing overfitting to training identities. This regularization is particularly beneficial for the open-set learning setting of person \acs{ReID}, as it encourages the model to learn more robust and transferable feature embeddings, as discussed in Section~\ref{sec:reidloss}, as described in Section \ref{sec:reidloss}.

\subsection{Validation strategy}
During training the learning of the models are monitored using the validation set introduced in \ref{trainingstragegyreid}. The performance are measured using the metrics from Section \ref{reidmethodevalmetric}: Rank1, Rank5, Rank10, Rank20 and \acs{mAP}.
\\\\
The model's performance was monitored through periodic validation:
\begin{itemize}
    \item For epochs 1 - 200: validation is performed every 10 epoch
    \item For epochs 201 - 350: validation frequency increases to every 5 epoch
\end{itemize}

\noindent This adaptive validation strategy allows for more frequent monitoring as learning rate drops, and the training approaches convergence. Training ran for a total of 350 epochs without early stopping, though checkpoints were saved every 10th epochs, as well as the best model based on \acs{mAP} score.

\subsubsection{Validation Strategy}
Validation was performed at the end of each epoch using the RELLISUR validation split. The validation pipeline computed both validation loss (L1) and validation \ac{PSNR} to monitor training progress. Model checkpoints were saved every 10 epochs, and the best model based on validation \ac{PSNR} was saved separately for final evaluation.

\subsubsection{Training from Scratch on RELLISUR}
The model was trained from scratch on the RELLISUR dataset using random weight initialization. RELLISUR provides paired \acs{LR} and \acs{HR} images captured under natural imaging conditions, as described in Section~\ref{sec:...}. During training, the images were not used at their full spatial resolution. Instead, patch-based training was employed, where aligned \acs{LR} and \acs{HR} patches of size \textit{64×128} and \textit{128×256} pixels respectively were randomly cropped from the original image pairs. This patch-based strategy is standard practice in super-resolution training, as it reduces memory consumption and increases the number of effective training samples.
\\\\
The RELLISUR validation split was used to monitor training progress and to select the best-performing checkpoint. An Adam optimizer with $\beta_1 = 0.9$, $\beta_2 = 0.999$, and a learning rate of $1 \times 10^{-4}$ was used. The best checkpoint was selected at epoch 113 based on validation \acs{PSNR}.

\subsubsection{Finetuning on DIV2K}
The best checkpoint from Stage~1 (epoch 113) was used as the starting point for finetuning on the \ac{DIV2K} dataset. The learning rate was reduced to $5 \times 10^{-6}$ in order to preserve the representations learned from RELLISUR while allowing gradual adaptation to the synthetically degraded \acs{DIV2K} data. 
\\\\
Validation was still performed on the RELLISUR validation split to monitor whether the model retained its ability to handle realistic, naturally degraded low-light and low-resolution image pairs, as opposed to overfitting to the synthetic degradation patterns present in \acs{DIV2K}.\\\\

Gaussian noise (mean: 0.0, std: 0.1) and Gaussian blur (kernel size: 7, sigma: [0.1, 2.0]) were applied only to the \acs{LR} images to simulate realistic degradations that might occur in surveillance footage. \section{Implementation of Sequential ReID and SR}
To fully asses the impact of implementing a \ac{SR} system with \acs{ReID}, a script was created to evaluate a sequential combination of the two models, where the data is first passed through the trained \acs{SR} model, whose output is then fed into the trained \acs{ReID} model. The efficiency of this setup is expressed with error metrics mAP and Rank-1, and can then be compared with other evaluation instances, such as the same \acs{ReID} model without the \acs{SR} module. 
\\\\
This sequential evaluation script is made to test both \acs{ReID} alone and also in combination with \ac{SR}. It was specifically made to fit only the \acs{OSNet} and \acs{EDSR} structure, as those are the main models used in this project. The dataloader discussed in \ref{imp_dataloading} was also used in conjunction with this script, but mostly with a distinct emphasis on the evaluation part, such as query and gallery for the relevant \acs{ReID} datasets.

\section{Implementation of End-to-end ReID and SR}
Since the \acs{SR} module was trained to upscale images, it is not specialized for the task of person \acs{ReID}. By combining the two modules end-to-end, the \acs{ReID} loss can flow back into the \acs{SR} module, forcing it to learn specific upscaling and cleaning operations which improve the final \acs{ReID} task. 
\\\\
To combine the two modules end to end, each model was downloaded from it’s respective Github repository. The models were then wrapped in a function which builds the model with the configuration befitting it’s size. \acs{OSNet} configuration can be seen in Table \ref{tab:osnet-config}, \acs{EDSR} configuration can be seen in Table \ref{tab:edsr-config}.
\\\\
To allow for losses to back-propagate through both modules, a new class was created with a combined forward pass. The forward pass takes an image as input, forwards it through the \acs{SR} module first and then through the \acs{ReID} module, with the option of also returning the \acs{SR} output to increase operation transparency. The class also allows for each module to be initiated with frozen weights, such that the possibility of the \acs{SR} module becoming a \acs{ReID} feature extractor is minimized. The frozen module can then be unfrozen with an unfreeze function.
\\\\
To benefit from the end to end integration of the two models, training was continued with pretrained weights from baseline \acs{OSNet} and finetuned \acs{EDSR}. \acs{OSNet} weights were frozen for the first 30 epochs, such that \acs{EDSR} could adapt to the new data being \ac{LR} images of people, instead of the more diverse nature of \acs{DIV2K} and RELLISUR. While only a classification loss back-propagated, it should still help specialize the model for the task, as can be seen in Section XXX. The learning rate for \acs{EDSR} was chosen, due to it being a middle point between the training and finetuning learning rate used during the standalone training. The learning rate for \acs{OSNet} was set to \texttt{1e-3}, such that it would drop to \texttt{1e-4} after the the first milestone, which coincides with \acs{OSNet} being unfrozen. This was chosen as the model had already learned the task of \acs{ReID}, and in this end-to-end training should focus on learning to extract features from \acs{SR} images. A second milestone was set at epoch 60 for final finetuning with the lowest learning rate. Training concluded at epoch 95, at which point the model had learned enough for a fair comparison with the other models, even if more performance could have been squeezed out.

\section{Deployment}
\label{deployment}
As the \acs{ReID} system was made with the intention to be utilized in a real-world setting, a script was created that allows it to be deployed on a third-party system with API functionality, as to facilitate its use by other external systems and users if needed.
\\\\
To ensure a more streamlined implementation of the system in future uses, the deployment was made with a Docker containerization setup. This ensures that relevant libraries, dependencies, and any other version-specific parameters needed to run the script, are present and being used. Furthermore, a requirements text file with used libraries and corresponding versions has also been included to allow reproducibility of the container or another virtual environment if needed.
\\\\
The deployment script utilizes the \texttt{FastAPI} library as its core framework for web related communication. This is specifically chosen because of its ease of use, yet powerful foundation, and tools. As deployment was not the primary focus point of this project, only a simple \texttt{GET} and \texttt{POST} request method were integrated in the script, which runs through hard-coded image directories located in the server. with little to no front end in mind. If implementation on a real system was the end-goal of this project, more work should be done to achieve an acceptable industry standard.
\\\\
The backend pipeline of the deployment script works by first processing the gallery and query image(s) from a \texttt{.JPG} filetype to a \texttt{base64} encoding and a tensor. The tensor contains the image with preprocessing applied, such as normalization and image resizing, which is done to align with the \acs{ReID} models architecture for optimal compatibility. Alternatively, the \texttt{base64} encryption is a copy of the non preprocessed image that is used to make file handling between the client and server more efficient. Subsequently, the tensors for query and gallery are computed by the \acs{ReID} model, which returns the best matches back to the client. A simple HTML setup has been created to integrate some visualization for the front end by displaying the returned matches with a ranking order and the original query image for comparison as seen in Figure \ref{fig:deployment_example}.
